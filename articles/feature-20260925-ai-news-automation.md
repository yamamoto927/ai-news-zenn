## はじめに

このリポジトリでは、生成AI関連のニュースを毎朝自動で集めて要約し、Zenn に **下書き** として投稿しています。人間は Zenn のダッシュボードで下書きを読むだけで、その日のニュースを把握できます。
この記事では、同じような仕組みを作りたい方の参考になるよう、全体の流れ、構成要素、そして設計上の工夫を紹介します。

## 全体の流れ

README.md に書かれている流れを要約すると、次のとおりです。

1. 毎朝 7:00 JST（22:00 UTC）に、Anthropic のクラウド上で Claude Code のルーティンが起動する
2. リポジトリを取得し、手順書である CLAUDE.md を読む
3. その日の記事が既にあれば、二重投稿を避けるため何もせず終了する
4. Web 検索でニュースを探し、記事ページを実際に開いて内容と日付を確認する
5. 重要度で選別し、下書きを最大4本作成する
6. 校閲エージェント（fact-checker）が出典と記事を突き合わせて指摘する
7. 指摘を反映し（必要なら再校閲、最大2回）、`main` に push する
8. Zenn の GitHub 連携で `articles/` の記事が取り込まれ、`published: false` の下書きとして表示される

1日の投稿は、重要トピック記事（最大3本）とその他まとめ（最大1本）の合計最大4本で、処理に失敗した日は失敗報告の下書きを残します。

本リポジトリでは定期実行のトリガーを使い、毎日 22:00 UTC に起動しています。ドキュメントには次のような点も書かれており、設計時に意識しておくと役立ちます。

- ルーティンは承認を待たずに自律的に動くため、プロンプトは「何をするか」「何ができれば成功か」を自己完結的に明示する必要がある

- 実行一覧で緑色の表示になっていても、それはセッションがインフラエラーなく終了したという意味にすぎず、タスクが成功したとは限らない。実際に何をしたかはセッションの記録を開いて確かめる
- 含めたコネクタのツールは、書き込みも含めて実行中に許可なく使えるため、不要なものは外すべき

README.md によると、このルーティンで使うのは Web 検索・Web ページ取得・ファイル操作・git・サブエージェント呼び出しに限られ、Gmail などの外部サービス接続は付けていません。

### 校閲サブエージェント（fact-checker）

`.claude/agents/fact-checker.md` に、校閲専用のサブエージェントを定義しています。公式ドキュメントによると、サブエージェントは特定の種類の作業を受け持つ専用のアシスタントで、それぞれが独立したコンテキストウィンドウ（会話の記憶領域）、独自のシステムプロンプト、指定されたツールだけを持って動きます。プロジェクト用のサブエージェントは `.claude/agents/` に置き、バージョン管理に含められます。

fact-checker の定義には、次のような特徴があります。

- 使えるツールを `Read, Glob, Grep, WebFetch` に絞っており、ファイルを書き換える手段を持たせていない
- 「記事を書いたのはあなたではありません」と明示し、記事の主張を疑って出典で裏付けられるかを確かめさせる
- 事実（出典にない主張、数値、固有名詞、主語や因果関係）、日付、著作権（丸写しや直訳の有無）、形式（`published: false`、出典URL、タイトルの誇張や文字数）をチェックする
- 指摘は `[要修正]` と `[確認推奨]` の2段階で返し、「指摘を水増ししない」ことも求めている

## 設計上の工夫

### 下書きに固定する

すべての記事は `published: false` で作成し、ルーティンが `true` にすることは禁止しています。既存記事の `published` も変更しません。

理由は Zenn の規約です。Zenn の利用規約（第4条）は、禁止事項として「スパムとみなされる行為（機械により自動生成された文章の投稿や同一内容の文章を繰り返し投稿する行為など）」を挙げています。一方、コミュニティガイドラインは生成AIの活用自体を禁止しておらず、内容の正確性を確認せずに投稿することや、フォロワー獲得やスコア上昇を目的とした記事の乱造を控えるよう求めています。
2026年3月10日のお知らせ「AIによるコンテンツ執筆に関するZennの方針について」では、「人が主体となる」ことの意味として、公開前に内容の正確性を検証したり、著者自身の経験や洞察をコンテンツに込めたりすることが挙げられています。また、ユーザーごとに期間あたりの投稿上限数を設けていることにも触れています。

このため本リポジトリでは、公開するかどうかは人間が内容を確認・加筆してから Zenn 上で手動で決める、という役割分担にしています。

### 開いて確認できた事実だけを書く

CLAUDE.md では、各ニュースについて一次情報（公式発表・論文・公式ブログ）か信頼できる報道の記事ページを **実際に開いて** 内容と日付を確かめることを求めています。

- 開いて確認できなかったニュースや、日付が対象期間外のニュースは載せない
- アクセスできないサイトがあれば、同じニュースを報じている別の媒体で確認を試みる
- 数値は出典に書かれているものだけを使い、噂やリークは「〜と報じられている」と明示する
- すべてのニュースに出典URLを付ける

### 書く役とチェックする役を分ける

執筆するメインのエージェントとは別に、fact-checker が出典と記事を照合します。サブエージェントは独立したコンテキストで動くため、執筆時の思い込みを引き継がずに記事を読み直せます。さらにツールを読み取り系に限ることで、校閲役が勝手に記事を書き換えることもありません。

指摘への対応も CLAUDE.md で決めています。

- `[要修正]` はすべて直す。出典で裏付けられない内容は、表現を直すのではなく削除する。削除で要点が成り立たなくなる場合はニュースごと外す
- `[確認推奨]` は表現を弱めるか削除する
- `[要修正]` を直したら、もう一度だけ校閲する（最大2回）。2回目でも残る箇所は削除する
- fact-checker を呼び出せなかった場合は、自分で出典と再照合したうえで push し、最終報告に「校閲エージェント未実行」と明記する

「直す」より「消す」を優先し、校閲の回数に上限を設けているのが特徴です。

### 失敗を下書きで知らせる

人間は Zenn の下書きしか見ないため、失敗したことも Zenn 上で気づけるようにしています。確認できたニュースが0件だった、情報源の多くにアクセスできなかった、手順を最後まで完了できなかった、といった場合には、「【要確認】」で始まる失敗報告を `articles/ainews-YYYYMMDD-error.md` として push します。失敗報告には、何を試みたか、どのサイトやコマンドでどんなエラーが出たか、人間が取るべき対応を書きます。`main` への push 自体が失敗した場合は、別ブランチへの push を試みます。

先ほど触れたとおり、ルーティンの実行一覧の緑色表示はタスクの成功を意味しません。「何も記事が来ない」状態を見逃さないために、失敗も成果物として残す設計にしています。

### ネットワークを必要な範囲に絞る

Claude Code のクラウド環境では、ネットワークアクセスのレベルを None（外部接続なし）・Trusted（パッケージレジストリや GitHub などの既定の許可リストのみ）・Full（すべてのドメイン）・Custom（独自の許可リスト）から選べます。既定は Trusted です。Custom では、許可するドメインを1行に1つずつ指定でき、既定の許可リストを含めるかどうかも選べます。

README.md によると、このリポジトリのクラウド環境は許可したドメインのみに制限した Custom の設定です。公式ドキュメントでは、Trusted の一覧にないドメインへアクセスさせたい場合は Custom を選んで許可リストに加えるよう案内されています。許可していないサイトにアクセスできなかった場合は、別媒体での確認を試み、それでも多くの情報源に届かなければ失敗報告を残す、という流れにつながります。

### その他の小さな工夫

- **二重投稿の防止**：その日のファイルが1つでもあれば何もせず終了する。直近7日分の記事も読み、既に取り上げたニュースは再掲しない
- **タイトルの文字数チェック**：CLAUDE.md によると、Zenn は70文字を超えるタイトルをデプロイエラーにするため、書いたあとに文字数を数えるコマンド例まで手順書に載せている
- **著作権への配慮**：要約は自分の言葉で書き、引用は必要な場合のみ1文以内・引用符付きとする
